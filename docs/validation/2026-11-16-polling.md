# Polling, lifecycle and facade validation

macOS arm64, AppleClang 21, OpenSSL 3, pinned Robotweax 0.3.3 and Haivision
1.5.7 with the documented KM/close patch. Release and optimized Release
AddressSanitizer/UndefinedBehaviorSanitizer builds both pass all eight CTest
groups. Instrumentation covers host, adapters and vendor libraries. The original
52-case transport matrix remains, including both providers transferring at once.

New tests exercise the public C++ facade, encrypted/plain Live and File transfers
in both directions and load orders, provider-local listener/connect/read events,
zero/finite/infinite waits, sticky/coalesced wake, registration changes during
wait, same-provider enforcement, concurrent send/receive versus abort-close,
terminal events, stale-generation reuse, preserved extensible event tails,
active-poller release cancellation, simultaneous facade transfers and shutdown
waking both providers. Callers still join workers before wrapper destruction.

## Native lifetime correction

Unpatched Haivision 1.5.7 intermittently crashed in encrypted close stress. Native
context tracing showed a KM handler using a crypto context after it was freed.
Neither OpenSSL 3 versus 4, the alternative EVP backend, nor pre-initializing the
crypto method table corrected it; those experiments were removed. The final
build retains the original OpenSSL backend and uses a two-handler lifetime patch:
[reviewable diff](../../providers/haivision-1.5.7-km-close.patch).

`closeInternal()` holds the connection lock while freeing the crypto object;
KMREQ/KMRSP processing now takes that same lock and checks closure. No payload,
ACK or scheduling path changes. CMake verifies the exact original core.cpp hash,
compiles a patched copy and records the resulting hash in provider build metadata.
The pinned upstream source tree stays unmodified. The regression stress passed
40 consecutive runs (20 per load order) after the fix. Earlier sanitizer-only
success did not detect the native timing race; it was not treated as proof of safety.

## Exploratory throughput comparison

[All raw samples and fingerprints](2026-11-16-polling-benchmark.json) contain five
randomly interleaved runs for each provider and each direct/C ABI/C++ facade path.
Each verifies 128 MiB after 8 MiB warmup, File/IPv4 loopback, plaintext, 32 KiB
calls, accounting disabled, identical options and vendor static targets. No other
task-owned build or test workload ran during measurement. This isolates dispatch,
I/O and the per-direction close gates; polling is tested separately. Native
library internal allocations and scheduling remain part of all three paths.

| Provider/path | Median Mbps | Change vs direct | CPU seconds/byte change |
| --- | ---: | ---: | ---: |
| Robotweax direct | 1930.5 | baseline | baseline |
| Robotweax C ABI | 1940.8 | +0.53% | -0.43% |
| Robotweax facade | 1937.9 | +0.39% | -0.30% |
| Haivision direct | 1207.7 | baseline | baseline |
| Haivision C ABI | 1175.8 | -2.64% | +1.75% |
| Haivision facade | 1555.6 | +28.81% | -15.46% |

Robotweax shows no observed regression in this narrow workload. Haivision is
inconclusive: direct samples range from 917.7 to 1582.7 Mbps and C ABI samples
from 848.0 to 1399.2 Mbps. The apparent facade speedup is not evidence of an
advantage; the C ABI result does not establish compliance with the draft 2%
throughput budget. Do not claim release performance qualification from these
shared-host samples. Controlled sustained message-rate, full-duplex,
many-connection, loss/encryption, polling latency and CPU measurements with
confidence bounds remain required. No throttling, extra payload copies or
worker-thread handoffs were introduced to make a benchmark pass.
