# Relay CPU against the original and a Haivision would-block fix — 20 November 2026

Local measurements on one shared macOS ARM64 desktop host, Release builds,
Robotweax SRT 0.3.4 and Haivision SRT 1.5.7. They compare behaviour on this host
and are not qualification data.

## Haivision reports "would block" through an exception

Haivision 1.5.7 signals a non-blocking call that cannot proceed by throwing and
catching a C++ exception inside the call. Measured natively, an idle receive
costs about 4.5 microseconds; through the dynamically loaded module it cost about
5.9, because locating unwind information for a loaded image is slower. The same
call costs about 0.14 microseconds on Robotweax.

On Haivision Live message connections the adapter now asks the socket for its
readiness first (`SRTO_EVENT`, tens of nanoseconds) and answers WOULD_BLOCK
itself. It does so only after a block that ended a short run of successful
calls, and a broken socket always goes to the native call so its error is
reported. Through the module an idle receive now costs about 0.07 microseconds.

What was tried and rejected, each with eight paired blocks of the File profile:

| Variant | File throughput vs native | Application-thread CPU vs native |
| --- | ---: | ---: |
| No pre-check (before) | 1.03, baseline varying 11% | 1.11 |
| Pre-check on File too | 0.972 (0.958 to 0.984) | 0.62 |
| Pre-check with a bounded re-ask loop | 0.923 (0.913 to 0.932) | 1.55 |

A saturated File transfer blocks on about 40% of calls and is ready again within
microseconds. There the exception doubles as a pause; answering at once makes the
caller sleep in its poller and costs about 3% throughput, over the 2% budget.
Re-asking in a loop was worse because each query takes vendor locks. File streams
therefore keep the native behaviour.

The saturated Live profile blocks about once in a hundred calls; with the
run-length rule the pre-check stays off there and the profile is unchanged
(module throughput 0.999, process CPU per byte 1.020 against 1.019 before, six
paired blocks).

## Relay CPU against the original application

A relay pair (UDP in, SRT between, UDP out) fed with a paced 1,316-byte
transport stream for 10 seconds; CPU is user plus system time of each relay
process, median of three runs. Every run delivered every packet, give or take
the final one.

| Relay | 5 Mbit/s sender | 5 Mbit/s receiver | 20 Mbit/s sender | 20 Mbit/s receiver |
| --- | ---: | ---: | ---: | ---: |
| Original application | 0.59 s | 0.68 s | 0.95 s | 1.17 s |
| This relay, Haivision | 0.81 s | 0.94 s | 1.84 s | 2.16 s |
| This relay, Haivision, `--coalesce-ms 2` | 0.82 s | 0.86 s | 1.09 s | 1.32 s |
| This relay, Haivision, `--coalesce-ms 10` | 0.52 s | 0.62 s | 0.87 s | 1.11 s |
| This relay, Robotweax | 0.83 s | 0.81 s | 1.89 s | 1.59 s |
| This relay, Robotweax, `--coalesce-ms 2` | 0.88 s | 0.74 s | 0.81 s | 0.66 s |
| This relay, Robotweax, `--coalesce-ms 10` | 0.60 s | 0.55 s | 1.55 s | 1.01 s |

- By default this relay uses about 1.4 times the original's CPU at 5 Mbit/s and
  about 1.9 times at 20 Mbit/s with Haivision. Per-thread CPU times and the
  coalescing experiment point to the cause: it wakes once per packet, while the
  original handles UDP input in batches on the library's 10 ms tick.
- With `--coalesce-ms 10` it is at or below the original with Haivision.
- Run-to-run variation on this host is large, roughly 10 to 30% between
  sessions; the Robotweax figures at 20 Mbit/s in particular are not ordered as
  one would expect. Treat single cells as indicative.
- Comparing the Robotweax and Haivision rows compares two libraries with
  different thread models, not this layer.

Before these changes the Haivision receiver used 2.50 s at 5 Mbit/s and 4.49 s
at 20 Mbit/s in a 15-second run, against 1.74 s and 2.98 s after them: about 30%
less, from the pre-check and from a leaner relay loop that reuses one read
buffer, builds no error text on the data path and waits as soon as its source is
empty instead of asking it a second time.
